# XIRASM 0.2.22

This release brings the Android platform surface into the assembler as generated
includes: the NDK's platform symbols, the constants its headers declare and the
byte offsets of the structures it hands back. A native source no longer spells a
library name by hand or counts a structure field, and the data behind both is
checked against the NDK on every run.

## Android platform catalog

- `include/os/android/` carries 25 platform libraries, 4,137 symbols and 4,416
  symbol/library rows, spanning API 21 to 35 and five ABIs, generated from the
  NDK's stub libraries. Each symbol records the library that provides it, the
  first API level it appears in, the GNU version tag and the ABIs that export it.
- `import("os/android/imports/liblog.inc")` gives you
  `android_import_log___android_log_write` plus a helper that welds the library
  name onto an import list. x86-64 uses a PLT stub, AArch64 a GOT slot, and the
  target picks the helper, so nothing in the source says `"liblog.so"`.
- `import("os/android/defs/native_activity.inc")` carries the other half: 1,168
  constants and 25 structure layouts with 161 field offsets, generated from the
  NDK headers. `android_layout_ANativeActivityCallbacks_onDestroy_offset64` is the
  offset the renderer example installs its callback at, and it is a generated
  fact rather than a counted one. Both Android data models are emitted, so a
  64-bit build and a 32-bit build read the offsets that apply to them.
- `import("os/android/catalog.inc")` answers questions by name, for tooling and
  diagnostics: which library provides a symbol, from which API level, on which
  ABIs. The table is parsed when the first query reads it, not when the file is
  imported.
- Everything is generated and reproducible: `--check` compares the tree against
  the NDK byte for byte, and the manifests record the NDK revision, the counts and
  a digest of the files used.

## Validation, including on a device

- `tests/os/validate_android_symbols.py` recomputes every fact with `llvm-nm`,
  independently of the generator: missing, extra, per-library API, per-symbol API,
  ABI mask and version tag all come out at zero differences.
- `tests/os/validate_android_constants.py` turns the generated constants and
  offsets into `_Static_assert`s, includes the same NDK headers and compiles them
  for LP64 and ILP32, so a wrong value fails a compiler rather than a program.
- `tests/os/check_catalog_vs_device.py` compares the catalog against the libraries
  a real device exports. On the Android 15 image used here 3,906 of 3,916
  catalogued symbols are exported, for x86-64 and AArch64 alike; the ten that are
  not are named: eight libz internals and one entry each in libvulkan and libEGL.
  They are stub-only entries, so importing one fails the load of the whole library.
- `tests/os/make_android_smoke.py` writes a source that imports a sample from
  every platform library, which turns loading it into a check of hundreds of
  symbol-to-library mappings at once. Both ABIs bind imports before the first
  instruction runs, so an uncalled import still has to resolve.

## Renderer example in both ABIs

- `tests/format/android_gl_demo/gl-demo-so-aarch64.asm` is the same GLES2 scene
  written in AArch64: platform calls load a GOT slot and branch to it, data labels
  are addressed with `adrp` plus `:lo12:`, and the ninth argument of
  `glTexImage2D` travels on the stack.
- `gl-demo-apk-universal.asm` puts both libraries in one package, so an emulator
  installs the x86-64 one and a phone the AArch64 one from the same archive.
  `tests/format/check_apk.py` verifies both entries, including the 16 KiB page
  alignment Android 15 requires.
- Rewriting the import sections through the catalog left the x86-64 library
  byte-identical at 6,496 bytes and the AArch64 one at 5,968 bytes, which is what
  the acceptance script reports.

## AArch64 and format fixes

- A `:lo12:` modifier used to lose the label's spelling, so `:lo12:MyData` looked
  for a lowercased name; `ldr xN, label` had the same defect. Both keep the source
  spelling now, and `tests/isa/arm/label_case.asm` pins every reference form in
  one fixture.
- A generated encoder that rejected an operand used to say only "operand value out
  of range". It now names the operand and the multiple it needs, which is what
  makes an unaligned literal load diagnosable; 136 diagnostics were added.
- The shared-object import tables were quadratic and recursive: a library with
  about 176 imports failed to assemble and 97 imports took 121 seconds. Both
  tables are single-pass prefix sums now, so 188 imports assemble in 6.85 seconds
  and 460 in 41 seconds.

## Documentation and editor support

- `include/os/android/README.md` and its Chinese pair describe the two access
  paths, the call form for each import mechanism, the API level facts, and where
  the data stops being true. `document/os-android.md` is the chapter that puts it
  together.
- `tests/os/check_android_docs.py` assembles every example in those pages, so the
  documented sources cannot drift away from the language.
- The VS Code extension ships the catalog and resolves its includes, so the
  constants complete inside the editor.
